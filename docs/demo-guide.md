# 项目演示路线与面试讲解稿

本文档用于把项目讲成一个完整的高并发应急物流平台。建议演示时不要从代码开始，而是先讲业务场景，再按角色操作，最后打开架构和高并发链路。

## 一句话定位

这是一个面向自然灾害、园区应急和企业集中采购场景的应急物流运力调度平台。平台围绕采购方、供应商、司机三类角色，支持限量物资发布、采购方高并发抢购、供应商确认供货、司机高并发抢运输单、订单发货地/目的地经纬度定位、运输追踪和三方履约评价。

可以这样开场：

> 我这个项目不是普通 CRUD 后台，而是把供应链采购和物流调度结合起来。场景是假设灾害发生后，发电机、净水设备、钢材、木方这类应急物资很紧缺，供应商会限量放货，采购方需要抢购，供应商确认后订单进入运输池，多个司机再抢同一个运输任务。系统里高并发主要集中在采购方抢购和司机抢单两条链路，我用了 Redis Lua、RabbitMQ、Redisson 锁和 MySQL 条件更新来保证不超卖、不重复接单。

## 15 分钟深度演示路线

### 第一段：业务背景

讲 1 到 2 分钟：

> 我设定的业务场景是应急物资采购和物流调度。比如灾害发生后，很多企业或政府单位要抢发电机、净水设备、钢材等物资。供应商因为库存有限，可能采用限量放货。采购方抢到后，供应商确认供货，订单进入运输任务池，多个司机再抢运输单完成配送。

要突出：

- 高并发不只在下单瞬间。
- 并发分布在采购方抢购、司机抢运输单、订单状态更新、通知推送。
- 物流平台和电商秒杀不同，后续履约链路更长。

### 第二段：系统角色和业务闭环

按角色讲：

1. 采购方：搜索供应商、下采购单、抢购限量物资、查看订单。
2. 供应商：维护库存、确认供货、扣减库存、拒绝订单。
3. 司机：查看推送订单、主动拉取运输大厅、抢单、开始运输、完成运输。

讲解话术：

> 三个角色不是孤立功能，而是围绕一张订单协同。订单从“待供应商确认”到“待司机接单”，再到“司机已接单”“运输中”“已完成”，每一步都写时间线，方便用户追踪，也方便后端排查问题。

### 第三段：高并发采购方抢购

核心接口：

```http
POST /api/purchase-orders/{orderId}/panic-buy
```

讲解顺序：

1. 请求先经过网关校验 Redis Token。
2. 业务服务校验订单状态。
3. Redis Lua 原子判断库存和重复抢购。
4. 成功后发送 RabbitMQ。
5. 消费者异步更新 MySQL。
6. Redisson 锁和 MySQL 条件更新兜底。

讲解话术：

> 抢购链路不能让所有请求直接打 MySQL，否则数据库会成为瓶颈，还容易出现并发超卖。所以我把第一层竞争放到 Redis，用 Lua 保证库存扣减和重复校验是原子的。抢到名额后不直接同步落库，而是发 MQ 异步处理，用户可以快速得到预占成功结果。MySQL 是最终一致的业务状态兜底。

可以引用压测结果：

> 我用 JMeter 做过 100、500、1000 并发压测，抢购名额设置为 1，最终每轮都只有 1 个请求成功，没有发生超卖。高并发下 P95 延迟会上升，说明本地单实例服务开始排队，这也是后续横向扩容和限流优化的方向。

### 第四段：高并发司机抢运输单

核心接口：

```http
POST /api/transport-orders/{orderId}/claim
```

讲解话术：

> 司机抢运输单和采购抢购类似，但业务含义不一样。一个运输订单只能绑定一个司机，所以我在 Redis 里给每个订单初始化一个运力名额，Lua 成功后写司机抢单 key 防重复，再发送 `transport:orderId:driverId` 消息。消费者拿到消息后使用 Redisson 锁，并通过 MySQL 条件更新 `driver_id` 和订单状态。如果消息重复消费，或者订单已经被其他司机抢走，条件更新会失败，不会造成重复接单。

强调三个关键词：

- 原子预占
- 异步落库
- 幂等兜底

### 第五段：物流位置建模

订单字段：

```text
originAddress
originLongitude
originLatitude
destinationAddress
destinationLongitude
destinationLatitude
```

讲解话术：

> 这个部分是我从 Fleetbase 这类物流平台吸收的思路。物流系统不能只关心订单状态，还要关心 Place，也就是发货地、目的地、司机位置和轨迹。当前版本订单已经记录发货地和目的地经纬度，发货地默认取供应商地址，目的地默认取采购方或 RFQ 配送地址；司机也可以手动上传到达节点，形成运输过程中的位置历史。待司机接单订单还会根据司机在线状态、距发货地距离和司机评分生成智能调度推荐，后续可以在这个基础上继续做地图展示、路线规划和 ETA 预估。

### 第六段：缓存、消息和可靠性

可以讲这些点：

- Redis Token：网关统一鉴权，服务端可主动失效。
- Cache Aside：供应商目录读多写少，缓存提升访问性能。
- RabbitMQ：订单创建、抢购、抢单异步化。
- 死信队列：异常消息可统计和补偿。
- Redisson 锁：消费者侧兜底，避免重复落库。
- MySQL 条件更新：最终业务一致性约束。

讲解话术：

> 我没有把 Redis 当简单缓存用，而是结合多种数据结构解决不同问题：Hash 存登录态，Lua 做原子抢购，GEO 查附近供应商，BitMap 记录司机出勤，ZSet 做高频供应商排行榜。调度推荐会把司机在线状态、位置距离和评分组合成可解释排序。三方履约榜会同时展示采购方、供应商和司机的评分，RabbitMQ 用于削峰和异步落库，数据库负责最终状态一致性。

## 面试官常见追问

### 1. 为什么不用数据库锁直接抢单？

回答：

> 数据库锁可以保证正确性，但高并发下所有请求都打到 MySQL，吞吐和响应时间都会受影响。我的设计是先用 Redis Lua 在内存层完成原子预占，把大部分失败请求挡在 Redis，成功请求再通过 MQ 异步落库。MySQL 仍然用条件更新兜底，所以不是放弃数据库一致性，而是把并发竞争前移。

### 2. Redis 预占成功后，MQ 或消费者失败怎么办？

回答：

> 这是典型最终一致性问题。当前项目里 RabbitMQ 消费失败会进入重试和死信统计，也有补偿接口。更完整的生产设计可以加本地消息表或事务消息，保证业务状态和消息发送一致；也可以给预占 key 设置 TTL，超时未落库则释放名额并告警。

### 3. 怎么保证不会重复接单？

回答：

> 有三层保证。第一层 Redis Lua 原子扣减运力名额；第二层 Redis 记录司机维度的抢单 key，防止同一司机重复提交；第三层 MySQL 条件更新要求订单必须是“待司机接单”且 `driver_id is null`，即使 MQ 重复消费，也只有第一次能更新成功。

### 4. 为什么还需要 Redisson 锁？

回答：

> Redisson 锁是消费者侧兜底，主要减少同一订单多条消息同时消费时对数据库的并发竞争。真正的最终一致性仍靠 MySQL 条件更新，所以即使锁失效，也不会破坏业务正确性。

### 5. 高并发下怎么扩展？

回答：

> 可以从几个层面扩展：网关和业务服务多实例部署，Nacos 做服务发现；Redis 做主从或 Cluster；RabbitMQ 增加消费者并调优 prefetch；MySQL 加索引、读写分离或分库分表；热点订单可以配合限流、排队和前端防重复提交。

### 6. 为什么项目里还有 Nacos？

回答：

> 项目是按微服务基础形态搭的，`gateway-service` 和 `auth-service` 通过 Nacos 注册发现。虽然现在本地只有两个服务，但架构上已经支持后续拆出订单服务、调度服务、通知服务。

### 7. 你从 Fleetbase 学到了什么？

回答：

> 我主要吸收的是物流平台的领域模型，而不是照搬代码。Fleetbase 这类系统会围绕 Order、Driver、Vehicle、Place、Waypoint、Tracking、Dispatch 建模。所以我把原项目从单纯供应链协同，升级成带订单运输池、司机抢单、发货地/目的地经纬度、智能调度推荐和运输追踪的物流调度平台。

### 8. 当前项目还有哪些不足？

回答：

> 当前版本重点验证业务闭环和高并发正确性，还不是生产级物流系统。后续可以继续做地图 SDK 接入、司机端连续后台定位、轨迹回放、ETA 预估、订单分派算法、服务拆分、限流熔断和完整消息事务。
